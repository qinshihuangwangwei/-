# 综测计分公示系统

让高校综测加分在**机制上**无法暗箱操作。

判断这个项目做得好不好，只有一条标准：

> 一个存心作弊的部长，在不动用数据库管理权限的前提下，能不能悄悄给关系户加分？

答案必须是"不能"。

---

## 它解决什么

| 病灶 | 应对 |
|---|---|
| 计分不规范 | 责任划分可配置，未指派禁止录入；每个计分项独立封顶 |
| 人情分 | 分数只能追加事件、不能修改；三级审批 + 72 小时申诉 + 匿名异议 |
| 事后无法追责 | 追加式账本 + 哈希链，谁在什么时候加了多少分、为什么，全部可查 |
| 假装统计过 | 公示页区分「已统计·0 条」与「未提交」——两者都是 0 分，意义相反 |
| 举报被报复 | 匿名异议完全匿名，数据库里也反推不出是谁提的 |

## 快速开始

```bash
npm test          # 跑全部不变量测试（833 项）
npm run smoke     # 端到端冒烟：全新数据库 → 可用状态（起真实服务、上传真实 xlsx）
npm run typecheck # 类型检查（运行时不依赖 tsc）

npm run dev       # 启动服务（start / server / serve 是同一入口）
npm run dev -- ./data/zongce.sqlite --host 0.0.0.0   # 局域网内手机可访问（默认 :3081）

npm run tick      # 手动跑一次定时任务（窗口推进、超时升级）
npm run ops       # 手动跑一轮运维（快照 + 链尾哈希存档 + 校验）
npm run ops -- ./data/zongce.sqlite --verify   # 只校验账本，不写任何东西
npm run admin:init -- ./data/zongce.sqlite teacher 学院老师   # 创建首个管理员
npm run passwd -- ./data/zongce.sqlite teacher                # 忘了密码时离线重置
```

**零运行时依赖、零构建步骤。** Node 24 直接执行 `.ts` 文件 ——
不需要编译器、不需要 node-gyp、不需要预编译二进制。
连 xlsx 解析、ZIP 解压、multipart 上传都是自己写的（`src/import/`、`src/http/multipart.ts`）。

首次启动会幂等播种参考数据（12 个部门 + 26 个计分项），并在数据目录生成
`.objection-key`。**这个密钥文件必须与数据库分开备份** —— 详见下文"匿名的边界"。

### 从零开始跑一轮

**第一步：创建管理员**（系统里没有自助注册为管理员的路径 —— 这是有意的）

```bash
npm run admin:init -- ./data/zongce.sqlite teacher 学院老师
```

它会打印一个初始密码。然后：

```bash
npm run dev        # 打开 http://127.0.0.1:3081
```

首次运行没创建管理员时，启动横幅会直接把上面那条命令打出来。

**忘了密码怎么办**

```bash
npm run passwd -- ./data/zongce.sqlite teacher      # 随机生成新密码
npm run passwd -- ./data/zongce.sqlite teacher 新密码  # 或自己指定
```

它只能重置**已有**账号，不会新建账号 —— 新建管理员仍然只走 `admin:init`。
这条边界是有意的：允许它创建账号，就等于给了一条绕开任免流程的后门。

接下来在浏览器里：

1. 用管理员账号登录（会被要求改密码）→ `/admin`：**创建综测周期**
2. `/admin`：**导入学生名册**（.xlsx / .csv，自动识别列 → 预览 → 确认）
   - 预览页会逐张工作表列出读到了多少人 —— **导入总有漏读**：
     格式畸形的行、源文件里学号写错的、学期中途转学插班的
   - 发现少了谁，去 `/admin/students` **手工补录**。补录的人可以立刻注册登录。
     每一次人工改动都会记入改动记录（谁、什么时候、改前改后），
     因为名册是所有分数的归属基础
3. `/admin`：**导入 B 项成绩**（来自教务，预览差异 → 确认）
4. `/chair/assignments`：把 26 个计分项指派给各部门（批量模板会跳过 4 个存疑项）
5. `/chair`：**进入录入状态**（有漏项会被拒绝，并列出具体是哪几项；
   进入时会自动建立全部「计分项 × 年级」切片）
6. 各部门录入 → 三级冻结 → 发布 → 申诉 → 公示 → 导出公示表

### 启动相关

- **默认端口 3081**（刻意避开 3080 —— 那是 DSH Web 开发工具界面的端口，
  撞在一起会以 `EADDRINUSE` 起不来，而原因看起来与它毫无关系）
- 换端口：`npm run dev -- ./data/zongce.sqlite --port 3082`
- 局域网访问：`npm run dev -- ./data/zongce.sqlite --host 0.0.0.0`
  （学生连同一个 WiFi，打开 `http://<你的电脑IP>:3081`）
- `npm run start` / `dev` / `server` / `serve` 是同一个入口

### 遇到问题

| 现象 | 原因与处理 |
|---|---|
| `Missing script: "server"` | 用 `npm run dev`（或 `start` / `serve`），四个名字都指向同一入口 |
| `端口 xxx 已被占用` | 换端口：`npm run dev -- ./data/zongce.sqlite --port 3082` |
| 打开页面只有登录框 | 还没创建管理员，见上面第一步 |
| 忘了管理员密码 | `npm run passwd -- ./data/zongce.sqlite teacher` |
| 导入后发现有学生没进来 | `/admin/students` 手工补录；先看看预览页的"逐表人数"，判断是漏读还是源文件的问题 |
| 学号重复导致有人被跳过 | 那是源文件里学号写错了 —— 报错会指出具体两行与两个姓名，去原始 Excel 里核对 |
| `unable to open database file` | 老版本的问题；现在会自动创建 `data/` 目录。仍报此错请检查路径是否可写 |

## 架构要点

设计上有四处刻意为之，都不是常规做法：

**1. 分数不存储，只重放。**
数据库里只有一张只能 INSERT 的 `score_events`。当前分数 = 把事件流按时间重放。
因此不存在"表和账对不上"的可能——表就是账。

**2. 不可篡改是物理事实，不是承诺。**
触发器禁止 SQL 层的 UPDATE/DELETE；哈希链让 `DROP TRIGGER` 之后的篡改也能被定位到具体哪一条；
每日链尾哈希外发存档，对付有完整数据库权限的人。三层各挡一类攻击，缺一不可。

**3. 时间窗口由时间推导，不由定时任务保证。**
72 小时申诉窗口、每级 24 小时审批时限，都由 `published_at` 与当前时刻算出。
定时任务只负责把结果落库。**任务挂掉，系统依然完全正确**——
否则它一定会在最需要工作的时候挂掉。

**4. 权限约束靠"入口不存在"，不靠"我们不会这么做"。**
管理员没有任何直接加分的 API（有否决权，无赠予权）；
窗口没有"延长"函数；匿名异议表里没有指向用户的列。
这些都有结构性断言测试守着，可以随时跑给任何人看。

### 运维

每日自动（也可 `npm run ops` 手动）：

1. **快照** —— `VACUUM INTO` 生成一致的数据库副本，留最近 30 份
2. **存档** —— 链尾哈希写成一份人能看懂的文本
3. **校验** —— 拿全部历史存档核对当前账本
4. **投递** —— 存档送到数据库之外

**失败会留下 `FAILED` 记录并显示成管理页上的红色告警。** 一个每天默默失败的
备份任务比没有备份更危险 —— 它让人以为自己有备份。

## 匿名的边界

异议的发起人**完全匿名**：`objections` 表里没有任何指向用户的列或外键，
只有 `HMAC(服务端密钥, 周期:学号)`。密钥存在数据库**之外**（`.objection-key`）。

| 谁能看到什么 | 结果 |
|---|---|
| 任何角色、任何界面 | 查不到 —— 系统里没有反查接口 |
| 拿到数据库文件的人 | 查不到 —— 密钥不在数据库里 |
| **同时拿到数据库与密钥的人** | **可以穷举学号反推** |

最后一行是这套方案的真实边界。**因此密钥文件必须与数据库分开保管、分开备份** ——
否则备份本身就是突破口。这个边界有测试守着（列集合断言、源码扫描），
可以随时跑给任何人看。

## 存档的边界

哈希链有一个已知弱点：**拿到完整数据库权限的人可以改掉内容并重算整条链**，
做到自洽。链校验照样通过，因为它只能证明"链是自洽的"。

对策是把"某一天账本长这样"这个事实**送到数据库之外**：

| 攻击者能做什么 | 触发器 | 哈希链 | 外部存档 |
|---|---|---|---|
| 用 SQL 改一条 | 🛑 挡住 | — | — |
| 拆掉触发器改一条 | — | 🛑 定位到具体哪一条 | — |
| 改完重算整条链 | — | ❌ 自洽了 | 🛑 与历史存档对不上 |

**但这个机制也有边界，必须说清楚：只有"篡改之前写下"的存档才能证明篡改。**
篡改之后重新生成的存档当然与篡改后的链一致。因此存档的价值完全取决于
它在时间上早于篡改，以及它被放在攻击者够不到的地方。

开发阶段存档落在 `data/anchors/`（设计文档 §10.1 的有意降级）。
**上线后应改为邮件外发到学院老师与两位主席** —— 否则存档与数据库在同一台机器上，
等于把证据和赃物放在同一个抽屉里。接口已经预留（`AnchorDelivery`）。

## 时间旅行的边界

`serve.ts --clock-offset <90m|4h|3d|3d12h>` 把整个系统的时间往前拨，
用来在几十秒内走完"发布 → 72 小时申诉 → 公示期 → 归档"。
启动时会打印醒目横幅，页面底部也会挂一条固定提示。**这些都是提醒，不是护栏。**

它有一个**不可逆**的副作用：

```
--clock-offset 不只影响"看起来的时间"。定时任务会调用 materialize()，
把推导出的状态**写进 terms.status**。而 deriveStatus 只能往前走：

  PUBLISHED --(发布 + 72h)--> PUBLIC --(公示期 + 公示窗口)--> ARCHIVED

一旦 status 被写成 PUBLIC，把时钟拨回真实时间**也不会退回去** ——
deriveStatus 里那段判断要求 status === "PUBLISHED" 才继续推进，
而它已经是 PUBLIC 了。
```

还有一个更隐蔽的后果：`canAppeal` 要求 `deriveStatus(...) === "PUBLISHED"`。
所以**带偏移跑过一次，那个周期的申诉窗口就永久关闭了** ——
即使真实时间还在 72 小时之内。

对策：**把时间旅行留给副本。**

```bash
cp data/zongce.sqlite data/preview/preview.sqlite
cp data/zongce.sqlite-wal data/preview/preview.sqlite-wal   # WAL 模式必须一起拷
npm run serve -- ./data/preview/preview.sqlite --port 3991 --clock-offset 4d
```

真库继续按真实时间走，两边的状态互不影响。`data/preview/README.md` 里有完整说明。
