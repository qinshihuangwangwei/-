# 综测计分公示系统 · 设计文档

- 日期：2026-09-26
- 状态：已通过设计评审，待写实现计划
- 目标读者：实现者（未来的自己 / 协作 Agent）

---

## 1. 问题陈述

高校综测计分长期由院学生会手工执行，存在三个具体病灶：

1. **计分不规范**——同一份 A 项细则，不同部门、不同年级的理解和执行不一致。
2. **人情分**——掌握加分权的人可以给自己人加分，且改完不留痕、无法追溯。
3. **事后无法追责**——分数用 Excel 传递，改了就改了，没有"谁在什么时候改了什么"的记录。

本系统要解决的不是"把 Excel 搬到网页上"，而是**让加分这件事在机制上无法暗箱操作**。判断设计好坏的标准只有一条：

> 一个存心作弊的部长，在不动用数据库管理权限的前提下，能不能悄悄给关系户加分？

答案必须是"不能"。如果能，设计就是失败的。

## 2. 范围

### 2.1 纳入系统（全流程自研）

| 部分 | 说明 |
|---|---|
| **A 项**（100 分） | 8 大类、25 个叶子计分项，学生会各部门负责录入 |
| **C 项**（附加分） | 由**学生办公室**主管，条目制，每笔须附材料 |

A 项与 C 项走**完全相同**的机制（录入 → 审批 → 冻结 → 申诉 → 公示）。这不是巧合，是刻意的统一抽象，见 §3。

### 2.2 排除在系统外（仅导入）

| 部分 | 说明 |
|---|---|
| **B 项**（100 分） | 学业成绩，来自教务。管理员用 Excel 一次性导入，学生仅可见自己的 |

最终总分在系统内合成：`S = A×0.3 + B×0.7 + C`。

### 2.3 明确不做（YAGNI）

- 不做微信小程序（学生会拿不到主体资质，且审核阻塞发版）
- 不做多学院 / 多租户（单学院部署）
- 不做 B 项成绩的课程级录入（教务系统是唯一真相源，重录只会引入新错误）
- 不做消息推送集成（站内消息足够；邮件只用于每日哈希存档）

## 设计原则：系统不该假装能判断它判断不了的东西

> 本节不参与编号，以免打乱后文所有交叉引用。

这是实现阶段确立、并在后续所有里程碑中适用的一条原则。它源自一次被需求方驳回的设计。

当时给申诉加了一条硬校验：**材料的上传者必须是申诉人本人**，否则拒绝提交。需求方的回应是：

> 申诉材料检验存在之后，一层一层由对应部门确定，最后才加分。

这句话推翻了我的设计，而且是对的。理由有两条：

1. **系统判断不了材料真伪，硬判只会误伤。** 班长代收材料、同学帮忙上传，在院里是常态。硬性拒绝会把"本人发起、他人代传"这种完全合理的情形一起挡在门外。
2. **系统假装能判断，反而制造了虚假的安全感。** 一条"上传者必须是本人"的校验，看起来关上了一道门，实际上挡不住任何真正的攻击——要冒用他人身份提交申诉，先得登录成那个人。

于是改为：**记录事实，显示事实，判断交给人。**

```
materialFromThirdParty: true      ← 材料上传者与申诉人不是同一人
attachment.uploadedBy: 2599000001
appeal.studentId:      2599000005
```

这不是错误提示，是**需要审批人注意的事实**。审批人看到它可以决定要不要向本人核实，也可以照常采信。判断权在人手里，系统只负责不让事实被隐藏。

**这条原则的适用范围**（后续每个里程碑都要拿它自查）：

| 场景 | 系统该做的 | 系统不该做的 |
|---|---|---|
| 申诉材料 | 记录上传者与 sha256，显示给审批人 | 拒绝非本人上传的材料 |
| 匿名异议（§8.3） | 记录理由与材料，交给主席+管理员双签裁决 | 判断举报内容是否"看起来可信" |
| 责任指派（§3.1） | 显示谁负责哪一项 | 猜哪个部门"应该"负责 |
| B 项导入（附录 C） | 报告命中率与差异，让人确认列映射 | 用 AI 猜哪一列是学号 |
| 分数上限（§5.5） | 拒绝超限写入并说明为什么 | 静默截断到上限 |

注意最后一行的对照：**"拒绝超限写入"是判断得了的事实**（6 > 6 是确定的），所以系统该管；
而"这份材料是不是真的"判断不了，所以系统不该管。**分界线是"能不能被确定地判定"，不是"重不重要"。**

## 3. 核心抽象：计分项（ScoringItem）

整个系统的设计支点是把 A 项子项和 C 项**建模成同一种东西**。

```
综测周期 Term（每学期一个）
 └── 计分项 ScoringItem          ← A 项 25 个子项 + C 项若干条目类型
      ├── 名称 / 分组（A1…A8, C）/ 分值上限
      ├── 责任部门 Department     ← 每学期由主席或管理员指派
      └── 分片 Slice = 计分项 × 年级   ← 部长把分片派给负责人
           └── 事件流 ScoreEvent        ← 追加式账本，只增不改
```

后果：A 项的「A7-3 体育类 × 2025 级」与 C 项的「办公室 × 2024 级」走完全相同的代码路径。权限检查、审批链、冻结、申诉路由、公示渲染**全部复用**。

### 3.1 为什么"计分项 → 责任部门"必须可配置

A 项细则每年会变，且各院归属不同。需求方（学生）本人也无法确认 12 个部门与 25 个子项的准确对应关系。因此：

- 系统预置一份**默认指派模板**（见附录 A）
- **每学期开始时**，主席或管理员必须逐项指派 `计分项 → 责任部门`
- **有任何一个计分项未指派，周期不允许进入录入状态**，系统直接列出漏项

未指派即禁止录入，而不是默认归某人——默认值就是人情分的温床。

## 4. 数据模型

### 4.1 实体

| 实体 | 职责 | 关键字段 |
|---|---|---|
| `User` | 账号 | 学号、姓名、班级、年级、密码哈希、状态 |
| `Term` | 综测周期 | 学年学期、状态、发布时间、锁定时间、公示结束时间 |
| `Department` | 部门（12 个） | 名称、启用状态 |
| `Membership` | **任职记录的真相源** | 用户 × 部门 × 角色 × 起止时间 × 任命人 |
| `ScoringItem` | 计分项 | 名称、分组、分值上限、排序 |
| `ItemAssignment` | 计分项 → 部门 | Term × ScoringItem × Department |
| `Slice` | 分片 | Term × ScoringItem × 年级 × 负责人 × 冻结状态 |
| `ScoreEvent` | **追加式账本** | 见 §5 |
| `Appeal` | 实名申诉 | 申诉人、计分项、理由、材料、各级审批状态 |
| `Objection` | 匿名异议 | 计分项、理由、材料、裁决结果（**无发起人列**） |
| `Attachment` | 材料 | 文件路径、哈希、上传人、上传时间 |
| `HashAnchor` | 每日链尾存档 | 日期、链尾哈希、外发邮件状态 |

**`Membership` 是身份的真相源，不是 `User` 上的字段。** 任职有任期、有任命人、有历史——部长换届后旧记录必须留存，否则无法回答"去年这 6 分是谁批的"。

### 4.2 层级归属

```
学院 → 年级（4 个）→ 班级 → 学生
```

年级由学号前两位或名册显式字段确定，不靠推断。

## 5. 追加式账本（防篡改的核心）

### 5.1 表结构

`score_events` —— **只允许 INSERT**：

| 字段 | 含义 |
|---|---|
| `id` | 主键 |
| `term_id` | 所属周期 |
| `student_id` | 分数归属的学生 |
| `item_id` | 计分项 |
| `delta` | 分值变化，**可正可负** |
| `event_type` | `ENTRY` / `CORRECTION` / `APPEAL_GRANT` / `OBJECTION_GRANT` / `REJECT` / `IMPORT` |
| `actor_id` | 操作者 |
| `reason` | 理由，**非空是数据库层约束** |
| `source_event_id` | 指向被更正 / 被审批的事件 |
| `appeal_id` / `objection_id` | 溯源到具体流程 |
| `created_at` | 时间戳 |
| `prev_hash` | 上一条事件的 `self_hash` |
| `self_hash` | `H(prev_hash ‖ 规范化后的本条内容)` |

### 5.2 不可篡改的三层保障

| 层 | 手段 |
|---|---|
| 应用层 | **不存在"改分"这个函数**。修改只能表现为追加一条新事件 |
| 数据库层 | `BEFORE UPDATE` / `BEFORE DELETE` 触发器 `RAISE(ABORT)`，见下方说明 |
| 验证层 | 哈希链。任何历史改动都会让后续所有 `self_hash` 失配，校验器能定位到被改的那一条 |

> **勘误（实现阶段发现）**：本文档早期版本写的是 `REVOKE UPDATE, DELETE ON score_events`。**SQLite 不支持 `REVOKE`**——那是 MySQL/PostgreSQL 的权限语法。SQLite 没有行级或表级权限系统，实际的强制手段是触发器：
>
> ```sql
> CREATE TRIGGER score_events_no_update BEFORE UPDATE ON score_events
> BEGIN SELECT RAISE(ABORT, 'LEDGER_IMMUTABLE: UPDATE forbidden'); END;
> CREATE TRIGGER score_events_no_delete BEFORE DELETE ON score_events
> BEGIN SELECT RAISE(ABORT, 'LEDGER_IMMUTABLE: DELETE forbidden'); END;
> ```
>
> 已验证有效（`tests/invariants/ledger.test.ts`）。
>
> **触发器的能力边界要说清楚**：它挡得住所有 SQL 层的 UPDATE/DELETE，但挡不住 `DROP TRIGGER` 之后的篡改——因为拿到数据库文件的人本来就能执行 DDL。**挡住 DDL 级攻击的不是触发器，是哈希链加外部存档**（§5.3）。这正是为什么三层缺一不可：触发器挡日常,哈希链挡内部,外部存档挡"有完整数据库权限的人"。

### 5.3 外部存档（对抗"有数据库权限的人"）

哈希链的已知弱点：拿到完整数据库权限的人可以重算整条链，做到自洽。

对策：**每日定时把当日链尾哈希通过邮件发送到学院老师与两位主席的邮箱**。外部存档一旦存在，重算全链也无法伪造历史存档。篡改必然暴露。

### 5.4 分数计算

```
单计分项得分 = SUM(delta) WHERE student, item
A 项 = SUM(所有 A 组计分项)
C 项 = SUM(所有 C 组计分项)
S = A × 0.3 + B × 0.7 + C
```

聚合结果可缓存（物化视图或缓存表），但缓存**永远不是真相源**——任何时刻都能从事件重放重建。

### 5.5 分值上限的处理

每个计分项配置 `分值上限`：

- **A 项**取细则规定值（见附录 A，合计 100 分）
- **C 项上限 12 分**（条目制累加，各条目分值之和不得超过 12）

**超限时拒绝写入，而不是静默截断。** 负责人录入一条会使该生该计分项超过上限的记录时，系统直接拒绝并在界面说明"该生 A7-3 已达上限 6 分"。

理由：静默截断会让"为什么他 6 分我也是 6 分，但我明明多参加了一个活动"变成无法回答的问题。拒绝写入则把上限这件事摊开在录入那一刻，负责人必须自己判断该给谁——判断本身也要写在理由里。

### 5.6 两种计分模式：累加制与基线制

**这是从真实数据里发现的，不是推导出来的。**

对 `25级综测成绩*.xlsx` 全量 147 名学生做取值分布分析后发现：**A6 遵纪守法（6 分）在四张班级表中全部为 5，无一例外**。

```
计算机2501-02 (57人)  col21(A6): 取值数=1  最常见=5(57)  ← 全表同一个值
大数据2501    (30人)  col21(A6): 取值数=1  最常见=5(30)  ← 全表同一个值
信计2501      (30人)  col21(A6): 取值数=1  最常见=5(30)  ← 全表同一个值
人工智能2501  (30人)  col21(A6): 取值数=1  最常见=5(30)  ← 全表同一个值
```

这说明 A6 **不是**"不申请就 0 分"的申请制，而是**基线制**：默认给 5 分，只有违纪才扣。

若系统只实现单一模式（默认 0 + 累加），A6 会给**每一个学生少算 5 分**。A 项满分 100、占综测 30%，5 分足以颠覆整个排名——而且这种错误是全局性的，不会有人发现，因为所有人的排名看起来"还是对的"。

因此 `ScoringItem` 必须带一个 `计分模式` 字段：

| 模式 | 基准 | 事件语义 | 适用 |
|---|---|---|---|
| `ACCUMULATE` 累加制 | 0 | 只能追加正向 `delta` | A 项绝大多数子项、C 项 |
| `BASELINE` 基线制 | 可配（A6 = 5） | 只追加负向 `delta`（扣分）；基准分由管理员配置并公示 | A6 遵纪守法 |

**基线分本身也必须公示。** "为什么大家都是 5 分"必须能在公示页回答，否则它会变成一个新的黑箱——一个所有人都一样的分，恰恰最不容易被质疑，也最容易被动过。

## 6. 状态机

```
DRAFT 筹备 → ASSIGNING 指派责任 → ENTERING 录入中
   → PUBLISHED 已发布（72h）→ PUBLIC 公示期（7 天）→ ARCHIVED 归档
```

| 转移 | 触发 | 守卫条件 |
|---|---|---|
| DRAFT → ASSIGNING | 管理员建周期、导名册、配细则 | 名册非空 |
| ASSIGNING → ENTERING | 主席或管理员 | **所有计分项均已指派责任部门**，否则列出漏项并拒绝 |
| ENTERING → PUBLISHED | 主席或管理员点击发布 | 至少一个切片已冻结 |
| PUBLISHED → PUBLIC | 定时任务，发布时刻 +72h | **自动，无人工延长入口** |
| PUBLIC → ARCHIVED | 定时任务，公示期满 7 天 | 自动，只读 |

### 6.1 发布时的部分完成处理

**不要求所有部门交齐即可发布。** 已冻结的分片计入；未冻结的分片显式标注「该分项统计未完成」并按 0 计入，同时该标注在公示期持续可见。

理由：若要求全交齐才发布，任何一个部门拖稿就能卡死全院，反而制造了新的要挟筹码。把"谁没交"公开，比堵住发布更有约束力。

### 6.2 分片未指派负责人怎么办

`ASSIGNING → ENTERING` 只要求**计分项已指派责任部门**，不要求每个分片都已指派负责人。但未指派负责人的分片：

- 在部门工作台上以「未分派」高亮显示，部长可见
- 在发布时与「未提交」同样处理：标注「该分项统计未完成」，按 0 计入，公示期持续可见

因此"没人认领"不会静默变成 0，而是变成一条**公开的、写着部门名字的未完成记录**。

### 6.3 时间窗口的不可协商性

`PUBLISHED → PUBLIC` 由定时任务执行，**代码中不提供任何延长窗口的功能**。主席也延长不了。

这不是不信任主席，而是把"卡点改分"这个行为从**可能**变成**不可能**。任何"紧急延长"的口子，最终都会被用在最需要它的那个人身上。

### 6.4 统计完成情况总览（针对"11 分从来没被统计过"）

对 `25级综测成绩*.xlsx` 全量分析发现（脚本见 `docs/analysis/analyze_distribution.py`）：

```
A3-3 青年大学习 (3分)：四张表 147 人，全部为 0
A8   易班工作   (8分)：计算机/信计全 0，人工智能仅个别有分，仅大数据有 8 人有分
```

**11 分在整届学生里实际上是空的。** 因为所有人都是 0，排名不受影响——但公示表上明晃晃列着"A8 易班工作（8分）"这一栏，看表的人会以为它统计过了。

**这恰恰是要消灭的那种不透明：一个从来没被使用的评分项，安安静静挂在公示表上装了很多年样子。**

因此公示页必须包含一个**统计完成情况总览**，逐个计分项显示：

| 显示 | 含义 |
|---|---|
| ✅ 已统计 N 条 | 分片已冻结，录入了 N 条加分记录 |
| ⚪ 已统计 · 0 条 | **分片已冻结，确认过没有任何人加分** |
| ⚠️ 未提交 | 分片未冻结 —— 这一项今年没人做 |
| ⚠️ 未指派 | 没有部门认领 |

**关键在于区分「已统计·0 条」与「未提交」。** 前者是"查过了，确实没有"；后者是"根本没人查"。两者在公示页上都是 0 分，但意义完全相反——把它们混在一起，就是让失职消失在沉默里。

没有这个总览，"未统计"和"统计结果是 0"在数据上无法区分；有了它，**哪个部门的哪一项今年没干活，全院都看得见。**

## 7. 权限模型

### 7.1 角色

`ADMIN`（管理员）、`CHAIR`（主席 ×2）、`HEAD`（部长 ×1/部门）、`DEPUTY`（副部长 ×2/部门）、`OWNER`（负责人，按分片指派）、`MEMBER`（干事）、`STUDENT`（学生）。

一个人可同时持有多个角色（副部长常兼某分片负责人）。权限判定对所有持有角色取并集。

### 7.2 角色产生

| 角色 | 产生方式 |
|---|---|
| ADMIN | 系统内置 / 学院老师 |
| CHAIR | **仅管理员可任命** |
| HEAD / DEPUTY | **主席可任免** |
| MEMBER | 学生提交加入申请 → 本部门部长审批通过 |
| OWNER | 部长将「计分项 × 年级」分片指派给本部门成员 |
| STUDENT | 名册白名单内注册即得 |

**主席能任免部长/副部，但不能变更干事的部门归属。** 干事换部门必须重新提交加入申请并由新部门部长审批，历史记录保留。行政任免权与成员归属权分离，避免两位主席联手把整个学生会换成自己的人。

**管理员账号**：数量不设上限（学院老师 + 开发者可各持一个），但系统初始化时通过一条一次性命令创建首个管理员，之后由既有管理员任命。**系统中没有任何"自助注册为管理员"的路径。**

### 7.2.1 三条系统级人事约束

实现阶段补齐，都由 `src/domain/membership.ts` 强制：

| 约束 | 内容 | 为什么 |
|---|---|---|
| **编制上限** | 主席 2 人；每部门部长 1 人、副部长 2 人 | 满编时必须先免后任——免职留下记录，直接换人不留 |
| **一人一职** | 一个账号同时最多一条在任任职记录 | 一个人不能既是 A 部部长又是 B 部干事 |
| **管理员 ≠ 主席** | 两种身份不可兼于一身 | 见下 |

第三条是**补上一个真实的漏洞**：

> 异议裁决要求"一位主席 + 一位管理员"双签，而双签靠的是**两个不同的账号**。如果同一个人既是管理员又是主席，他一个人就能凑齐两组签署——双签就退化成了一个人签两次。

这条约束在权限矩阵里表达为 `signerGroups: [["CHAIR"], ["ADMIN"]]`：两个签署组**互不相交**，因此没有任何单一角色能满足全部签署组。矩阵测试里有一条断言专门守着"签署组两两不相交"。

### 7.4 两条硬规则（写进核心，不做成配置）

**规则一：管理员有否决权，没有赠予权。**
管理员可参与异议裁决以制衡主席，但**系统中不存在任何"管理员给学生加分"的入口**。管理员能阻止一个错误的分被加上去，不能主动把分送给谁。

若管理员需要修正数据，唯一途径是走与主席的双签裁决流程，全程留痕并公示。否则只是把人情分从学生会搬到了管理员手里。

> 边界澄清：矩阵中管理员可「批准分片（冻结）」，这不违反本规则——批准只能让已录入的值生效，**不能改变任何分值**。它存在的意义是部长缺席时的运营兜底，且该动作留痕。

**规则二：与自己相关的一律回避。**
任何人不得：
- 审批自己的申诉
- 审批自己录入的分片
- 裁决涉及自己本人分数的异议
- 裁决自己所在班级的异议

审批链上撞到自己，**自动跳过该级**并在流程记录中标注跳过原因。

## 8. 三条业务流程

### 8.1 流程一：录入与冻结

```
负责人录入（立即入账，产生 ENTRY 事件）
   → 负责人提交分片
   → 副部长复核
   → 部长批准 → 分片 FROZEN
```

**为什么录入即入账，而不是逐条审批？** 因为账本只增不改，负责人自己也无法抹掉已录的内容——留痕已经天然存在。逐条审批只会把 104 个分片变成上千次点击，审批人最后必然闭眼点通过，反而失去意义。审批的粒度定在**分片级**。

规模：约 26 个计分项 × 4 个年级 = 104 个分片/学期，部长可批量批准。

### 8.2 流程二：申诉（实名 · 发布后 72 小时）

- **对象**：必须是**某一个具体计分项**，不接受对总分的申诉（否则无法路由）
- **发起人**：仅本人，实名
- **强制**：理由非空 + 材料必传，缺一不可提交
- **链路**：该「计分项 × 年级」的负责人初审 → 副部长复审 → 部长终审
- **生效**：三级全过才追加 `APPEAL_GRANT` 事件
- **驳回**：任一级驳回即终止，写 `REJECT` 事件并强制填写理由
- **次数**：同一计分项被驳回后不可重复申诉
- **时限**：**每级 24 小时，超时自动升级** —— 负责人超时 → 直送副部长；副部长超时 → 直送部长；部长超时 → 转主席 + 管理员双签。超时升级动作本身也留痕
- **跨窗口**：72 小时内已提交的申诉，即使窗口关闭也继续走完流程（延迟是审批人的责任，不是学生的）

**超时自动升级的理由**：学生的申诉窗口只有 72 小时。如果审批人"忘了处理"，学生的权利就被拖没了——这本身就是一种不透明的权力。让拖延失效，是让流程可信的前提。

### 8.2.1 材料真伪不由系统判定

实现阶段一度加过一条校验：**材料的上传者必须是申诉人本人**，否则拒绝提交。后来去掉了。理由有两条：

1. **它会挡掉正当流程。** 材料由班长代收、同学帮忙上传，在院里是常态。硬性拒绝会把"本人发起、他人代传"这种完全合理的情形一起挡在门外。
2. **它挡不住真正的攻击。** 要冒用他人身份提交申诉，先得登录成那个人——那是身份认证（§9）该管的事，不是材料表该管的事。

**系统的职责是把事实摆到审批人面前，判断真伪是三级审批的事。**

因此上传者信息被完整记录，并通过 `appealDetail()` 在审批界面显示：

```
materialFromThirdParty: true      ← 材料上传者与申诉人不是同一人
attachment.uploadedBy: 2599000001
appeal.studentId:      2599000005
```

**这不是一个错误提示，是一个需要审批人注意的事实。** 审批人看到它可以自行决定要不要向本人核实——也可以照常采信，因为代传本身完全正常。判断权在人手里，系统只负责不让它被隐藏。

配套措施：

- **材料哈希（sha256）一并记录。** 审完之后把材料换掉是另一个攻击面，哈希让它可被发现。
- **代写申诉没有"匿名"这一说。** 申诉永远记名在被申诉人名下，必须走完三级，每一步的操作人都进入公示期可见的记录。系统不给"偷偷替人加分"提供任何入口。
- **真正的第一道门是身份认证。** 提交申诉必须登录成那个学生本人。这一点在 §9 里保证，不能靠材料归属来替代。

### 8.3 流程三：异议（匿名 · 公示期 7 天）

存在的理由：72 小时窗口内学生**只能看到自己的分**，因此无法发现"别人被乱加分"。等到公示期能看到了，系统已经锁死。若不设此通道，"给关系户多加分"这一最典型的人情分将绕过全部检查。

- **对象**：他人的**某一个具体计分项**
- **发起人**：任何学生，**完全匿名**
- **强制**：理由非空 + 材料必传
- **限流**：每人每公示期最多 2 条，同一计分项同一理由不可重复提交
- **裁决**：主席 + 管理员**双签**
- **效果**：成立则追加 `OBJECTION_GRANT` 事件，**可加可减**
- **公示**：所有异议及处理结果全部进入公示页，未处理的显示「待处理」

### 8.4 匿名的实现：查不到，而不是不查

异议表**不存储发起人身份**，只存 `HMAC(学号, 服务端密钥)`。

- 同一学号多次提交得到相同哈希 → **限流照做**
- 哈希不可逆 → **任何角色、任何界面、包括直接翻数据库，都无法还原发起人**
- 系统**不提供**任何按哈希反查用户的接口

由此产生的代价必须被接受：**主席和管理员只能凭材料裁决，无法追问补充**。因此异议表单必须强制结构化——必须选定具体计分项 + 填理由 + 传材料，否则提交不了。含糊的"我觉得有人作弊"根本进不了系统。

### 8.5 公示期满仍有未裁决的异议

公示期结束（`PUBLIC → ARCHIVED`）时，若仍有异议处于「待处理」：

- 该期**不允许归档**，自动顺延，并在对主席和管理员的看板上高亮告警
- 顺延期间系统仍保持公示期的只读状态，学生可见全部数据
- 顺延没有固定上限，但**每一个顺延日都会写一条记录并显示在公示页上**——拖延的代价是被公开

理由：若允许带着未处理异议归档，那么"拖着不办"就成了最省事的应对方式，公示期纠错权会被行政惰性架空。

> 变更记录：原始需求为"实名异议"。经讨论改为匿名，理由是实名举报在院学生会权力结构下会使举报人承受报复风险，导致该通道事实上不可用。

## 9. 身份与认证

- 管理员导入「学号 + 姓名 + 班级」名册作为白名单
- **初始密码 = 身份证后 6 位**
- 学生首次登录用「学号 + 身份证后 6 位」→ **强制设置新密码** → 之后用新密码登录
- 忘记密码由本部门部长或管理员重置为初始密码，并再次强制修改

**为什么不用「学号 + 姓名」两要素**：这两项在同班同学之间是公开信息，无法阻止冒名注册。身份证后 6 位不属于公开信息，且学生本人都记得。

**存储要求（硬性）**：身份证后 6 位在本系统中**只作为密码存在，必须以密码哈希（argon2id 或 bcrypt）存储，严禁明文落库**。它不承担任何身份标识功能——两个人恰好后 6 位相同是完全允许的，因为它是密码不是 ID。

### 9.1 名册从哪来（开发阶段的现实约束）

当前处于**个人开发阶段，无学校支持**，拿不到含身份证号的教务名单。因此名册导入分两级：

| 级别 | 名册内容 | 谁能注册 |
|---|---|---|
| **基础** | 学号 + 姓名 + 班级 | 学生首次登录时**自行输入**身份证后 6 位作为初始密码（系统只做格式校验，不比对来源） |
| **完整** | 学号 + 姓名 + 班级 + 身份证后 6 位哈希 | 系统比对，安全性更高 |

基础级别下，"初始密码 = 身份证后 6 位"的安全性完全依赖**身份证后 6 位不是公开信息**这一事实，而不是依赖系统校验。这在开发阶段是可接受的：冒名者需要知道目标同学的身份证号，成本远高于收益。

**这是有意的降级，不是疏漏。** 待获得学校支持后，升级到完整级别只需在名册导入时多带一列，应用代码不变。

## 10. 技术栈与部署

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Node.js + TypeScript | 前后端同语言，类型系统对权限矩阵和事件类型这类易错点帮助大 |
| 数据库 | SQLite（WAL 模式） | 2000 人以内绰绰有余；**单文件备份极简单**；可平滑迁移至 Postgres |
| 前端 | React + TypeScript | 手机浏览器优先 |
| 备份 | 每日 SQLite 快照 + 链尾哈希邮件存档 | 快照防丢数据，邮件防篡改 |

规模上限：约 2000 学生/学院，单机足够。

### 10.1 部署分两个阶段（当前无学校支持）

| 阶段 | 环境 | 形态 |
|---|---|---|
| **现在（开发）** | 开发者本机 | `npm run dev` 直接跑，SQLite 文件落在本地，学生用局域网 IP 访问。**不涉及域名、备案、证书、云主机** |
| **将来（上线）** | 云主机或学院服务器 | 单机 + systemd/Docker + Caddy 自动 HTTPS |

**开发阶段刻意回避的外部依赖**：域名备案（无学校支持时几乎办不下来）、HTTPS 证书、邮件外发。

因此**哈希链的每日外部存档在开发阶段降级为本地文件**（`backups/anchor-YYYY-MM-DD.txt`），邮件外发作为可插拔的通知通道，等有真实邮箱后再接。降级不影响任何安全性质——存档依然是"应用之外"的，只是从邮箱变成了另一个目录。

> 待办：一旦确定上线环境，需补做域名备案与 HTTPS，并把外部存档从本地目录切回邮件。

## 11. 测试策略：测不变量，不测功能

这套系统的价值全部集中在几条硬性质上，测试直接盯它们。

| 不变量 | 验证方式 |
|---|---|
| 账本不可改删 | 直接对 `score_events` 发 UPDATE / DELETE，断言被数据库拒绝 |
| 哈希链可验证 | 手工篡改一条历史事件，断言校验器报错并**指出被篡改的位置** |
| 分数由重放得出 | 随机事件序列重放结果 == 缓存值 |
| 权限矩阵 | 由矩阵**驱动生成**测试用例（7 角色 × N 动作全覆盖） |
| 状态机 | 非法转移必须抛错（如 PUBLISHED 状态下直接改分） |
| 72h 窗口 | 时间注入：68h 可申诉，73h 被拒 |
| 回避规则 | 申诉人 == 负责人时，断言该级被跳过并记录原因 |
| 范围隔离 | 部长只能读到本部门负责计分项的数据，跨部门读取返回空 |
| **匿名性** | 断言 `objection` 表**不存在**指向用户的列；断言代码库中无任何反查接口 |
| 管理员无赠予权 | 遍历全部 API，断言不存在"ADMIN 直接加分"的路径 |

最后两条是设计承诺的守门人——**匿名靠"查不到"保证，权力约束靠"入口不存在"保证**。

## 附录 C：B 项导入设计

### C.1 设计立场：用确定性识别，不用 AI

最初的设想是"接入 AI 防止格式太严苛导致失败"。**最终决定不接 AI**，理由有三条：

1. **AI 解决的问题在这个场景里不存在。** B 项的唯一来源是教务系统导出，必然是规整的二维表——而扫描件、手写、非结构化文本才是 AI 不可替代的地方。真正的难点不是"格式严苛"，而是"哪一列是学号、哪一列是 B 分"，这个问题用正则可确定性解决。
2. **AI 会打断审计链。** 整套系统的价值在于"同一输入 → 同一结果 → 随时可重放"。B 项导入若由 AI 解析，就是整条链上唯一不可复现的环节，而公示期恰恰要回答"这个 B 分是怎么来的"。
3. **隐私上说不通。** 一个以"数据可信"为卖点的系统，不该把全院学生的学号与成绩送到第三方 API。

**替代做法：把"宽容"体现在诊断上，而不是体现在猜测上。** 导入失败时给出具体到列和数字的解释，而不是笼统的"格式错误"。

### C.2 流程

```
上传文件 → 保存原件（记 sha256）→ 遍历所有工作表识别候选列
  → 预览（识别结果 + 统计 + 与上次的差异）→ 管理员确认/修正列映射
  → 提交 → 事务内 UPSERT → 写审计记录
```

### C.3 列识别规则（确定性）

| 目标列 | 判据 | 选择优先级 |
|---|---|---|
| **学号** | 列内 ≥80% 单元格匹配 `^\d{8,12}$`，且这些值在名册中的**命中率 ≥80%** | 命中率最高者 |
| **B 分** | 列内 ≥90% 可解析为数字且落在 `[0, 150]` | 表头含「成绩 / 分数 / 综合 / 学业 / B」者优先 |
| 姓名（可选） | ≥80% 为 2–4 个汉字，且名册命中率 ≥80% | 用于交叉校验 |
| 班级（可选） | 表头含「班级 / 班」，或 ≥80% 匹配 `^.+?\d{4}$` | 用于交叉校验 |

**名册命中率是最强判据**：它直接拿数据去名册里验，而不是猜表头文字。命中率低的列，表头写什么都无关紧要。

**多重候选时不自动决定**：若识别出多组可行的 (学号列, B 分列) 组合，列出全部候选交由管理员选择，系统不替人做判断。

### C.4 失败诊断（关键要求）

任何一步失败都必须给出具体到列与数字的解释。**禁止"格式错误"这类无信息报错。**

```
❗ 未找到学号列
   第 3 列有 328 个 10 位数字，但仅 12 个能在名册（328 人）中找到，命中率 3.7%
   可能原因：该列是身份证号 / 名册导错了 / 学号带了前缀字符
```

### C.5 差异预览（提交前的最后一道闸）

```
本次导入将影响 328 条记录
  ✅ 296 人：B 分无变化
  ⚠️  30 人：B 分变动          ← 可展开逐条查看
  ❌   2 人：学号不在名册中，将被跳过   ← 可下载为 CSV
  ➕   0 人：名册中有但本次文件中缺失
```

若变动比例超过阈值（默认 30%），要求管理员**二次确认**。列映射错位的典型症状就是这个比例异常——这是比任何格式校验都有效的兜底。

### C.6 幂等性与审计

- **幂等**：以 `(term_id, student_id)` 为唯一键 UPSERT，同一文件导入两次结果相同
- **原始文件永久保留**在 `data/imports/`，文件名含 sha256
- **每次导入写一条审计记录**（`import_jobs` 表，append-only）：原始文件哈希、识别出的列映射、解析记录数、跳过数、操作人、时间

日后任何时候都能回答："这个人的 B 分是从哪份文件、哪一列、哪一次导入来的。"

### C.7 B 项不进入 A/C 账本

`score_events` 账本只承载 A 项与 C 项（由人给出、需要理由和材料的分）。**B 项是导入的事实数据，不产生 `delta` 事件**，单独存 `b_scores` 表。

但**导入动作本身必须可审计**（见 C.6）。区分标准是：**账本记录"人的判断"，导入记录"数据的搬运"。**
