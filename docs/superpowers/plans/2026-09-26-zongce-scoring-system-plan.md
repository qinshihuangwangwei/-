**M3.4 的实现决策**：

1. **快照用 `VACUUM INTO` 而不是复制文件。** 复制正在写入的数据库（WAL 模式下尤其）
   可能得到半截状态 —— 平时看不出问题，直到你真的需要恢复它的那一天。
2. **存档是给人看的文本，不是 JSON。** 它要被邮件发出去、被人肉眼看、
   被复制粘贴进聊天记录。一份能被看懂的东西更适合这个场景。
3. **失败必须看得见。** 每一步都写 `ops_runs`，失败带原因、带重试次数，
   并在管理页显示成红色横幅。一个每天默默失败的备份任务比没有备份更危险 ——
   它让人以为自己有备份。
4. **重试不是可选的。** 备份失败往往是暂时的（磁盘满、文件被占用），
   而运维任务没人盯着。不重试的话，一次瞬时失败就等于当天没有备份。
5. **每日运维不参与授权。** 它与定时任务一样只是物化与归档；
   窗口关闭、超时升级全部由时间推导，从不依赖它。

**M2.4 的实现决策**：

1. **权限强制落在路由层，且是结构性的。** 每个路由必须声明 `action`（漏写编译不过）；
   免登录路由构成一份固定清单（多一个测试就失败）；路由表里不存在任何
   让管理员"一个人就能加分"的动作。
2. **整个 HTTP 层可以在不开端口的情况下被测试。** 请求与响应都是普通对象，
   `dispatch()` 直接调用。因此"服务端确实拒绝了"这件事是被测过的，
   而不是靠手工点页面确认。
3. **附件暂时是文本。** 真正的文件上传留到 M3 —— 但"材料必传"这条硬约束没有被绕过，
   文本说明同样落 sha256，事后可核对。宁可先跑通，也不让它暂时不生效。

**M2.3 的实现决策**：

1. **匿名的边界被写进代码注释与设计文档，而不是宣称"绝对匿名"。**
   指纹是 `HMAC(服务端密钥, 周期:学号)`，密钥**不在数据库里**。因此翻遍数据库推不出是谁；
   但同时拿到数据库与密钥的人可以穷举学号反推。这个边界必须说清楚 ——
   代价是密钥文件要与数据库分开保管、分开备份。
2. **分歧用返回值表达，不抛错。** 抛错会让整个事务回滚，"两人吵过一架"这件事
   在事后完全看不到，公示期照样能归档 —— §8.5 就白写了。
3. **公示期顺延由时间推导**：`deriveStatus` 在 PUBLIC → ARCHIVED 这一步多查一次
   待裁决异议数。因此**定时任务没跑也不会错误归档**，与 72 小时窗口同源。

**M2.1 的两个实现决策**（与计划的偏差）：

1. **`OWNER` 不是账号的固有角色，而是由资源决定的作用域。**
   谁是某切片的负责人是 `slices.owner_id` 说了算，不进 `Actor.roles`。
   矩阵里保留 OWNER 只是为了让清单读起来完整；真正的约束在 scope `slice-owner` 上。

2. **权限的运行时强制落在路由层（M2.4），不在领域函数里。**
   `slice.record()` 等函数当前检查的是"你是不是这个切片的负责人"——那是**作用域**，不是角色。
   角色判定需要 `Actor`，而 `Actor` 只有路由层能从会话里解析出来。
   因此 M2.1 交付矩阵 + `Actor` 解析 + 矩阵驱动的测试；M2.4 让每个路由都过 `assertCan`。

**阶段一完成时的额外发现**（实现过程中暴露、已回填文档或代码）：

1. 设计文档写的 `REVOKE UPDATE, DELETE` 在 SQLite 里**不存在**——已勘误为触发器方案，并说清触发器的能力边界（挡不住 `DROP TRIGGER`，那一层由哈希链负责）。
2. 申诉超时留痕原先只在定时任务里写——若任务没跑，"没人拖过"与"任务恰好没跑"在事后无法区分。已改为**任何人触碰申诉时立即落库、且独立提交**，这样"超时后还想驳回"被拒绝时，超时证据不会被连带回滚。
3. 申诉材料一度加了"上传者必须是申诉人本人"的硬校验，**后经需求方指出并撤销**。理由见设计文档 §8.2.1：它会挡掉班长代收、同学代传这类正当流程，而真正的第一道门是身份认证（M2.1）。改为**记录并在审批界面显示**材料来源，由三级审批自行判断真伪。

## 0. 总策略：先纵向打通，再横向铺开

这个项目最大的风险不是"写不完"，而是**把状态机、账本、审批链这三样最容易想错的东西，藏在几十个页面后面，等到最后才发现设计不对**。

因此：

| 阶段 | 目标 | 判断标准 |
|---|---|---|
| **阶段一** ✅ | 用最少的代码让**一个**计分项走完全流程 | 状态机与账本设计被证伪或证实 |
| **阶段二** | 横向铺开到 25 + N 个计分项、12 部门、真实身份权限 | 换数据不改代码 |
| **阶段三** | 加固：匿名异议、哈希存档、导入导出、部署 | 能交给下届学生会自己跑 |

阶段一**故意不做**：注册登录、漂亮界面、B 项导入、导出、邮件、多部门。全部硬编码，只为验证内核。

## 技术栈实况（与计划的偏差）

计划里写的是 `Node.js + TypeScript + SQLite`。实际落地时发现 Node 24 自带两样东西，于是**整个项目做到了零运行时依赖、零构建步骤**：

| 计划 | 实际 | 收益 |
|---|---|---|
| better-sqlite3 之类的驱动 | **`node:sqlite`（内置）** | 没有原生依赖 → 不需要编译器、不需要 node-gyp、不需要预编译二进制。对学生自己部署这件事是决定性的 |
| vitest / jest | **`node:test`（内置）** | 少一个依赖树 |
| tsx / ts-node / 构建 | **Node 原生类型擦除** | `node src/db/ledger.ts` 直接跑 `.ts`，没有构建产物 |

`typescript` 与 `@types/node` 只用于 `npm run typecheck`（`tsc --noEmit`），不参与运行。

`tsconfig.json` 开启了 `erasableSyntaxOnly`：它强制只使用可以被类型擦除的语法（禁用 `enum`、`namespace`、构造函数参数属性），从而保证"Node 能直接跑"这件事不会在将来被无意破坏。

## 1. 目录结构（一次定好，后面只填不改）

```
src/
  db/
    migrations/          # 顺序编号的 SQL 迁移
    ledger.ts            # 追加事件 / 重放 / 哈希链
    verify.ts            # 链校验器（可定位篡改位置）
  domain/
    term.ts              # 周期状态机
    slice.ts             # 分片录入与冻结
    appeal.ts            # 申诉链路
    objection.ts         # 匿名异议
    permission.ts        # 权限矩阵 —— 单一真相源
  jobs/
    scheduler.ts         # 定时任务（72h 锁定、超时升级、每日存档）
  auth/
  http/routes/
  ui/
tests/
  invariants/            # 设计文档 §11 的不变量测试
```

**关键约束：`domain/permission.ts` 是权限的唯一真相源。** 运行时检查和测试用例生成都从它读，不允许在路由里手写 `if (role === 'HEAD')`。

## 2. 阶段一：走通一条线（tracer bullet）

**范围**：1 个学院、1 个计分项（用 A7-3 体育类 6 分）、1 个年级、1 个部门、5 个学生。身份用种子数据硬编码，没有注册。

### M1.1 账本地基

**交付**
- 项目脚手架（Node + TS + SQLite/WAL + 迁移工具）
- `score_events` 建表，含 `prev_hash` / `self_hash`
- 数据库层物理保护：`REVOKE UPDATE, DELETE` + `BEFORE UPDATE/DELETE` 触发器
- `ledger.append()` / `ledger.replay()` / `verify.chain()`

**验收测试**（`tests/invariants/ledger.test.ts`）
- [ ] 直接 `UPDATE score_events SET delta=999` → 断言被拒绝
- [ ] 直接 `DELETE FROM score_events` → 断言被拒绝
- [ ] 追加 N 条事件后 `replay()` 结果 == 逐条手工累加
- [ ] 篡改中间某条（绕过触发器直接改文件）→ `verify.chain()` 报错并**指出是第几条**
- [ ] `reason` 为空的事件 → 断言插入失败

> 最后一条容易漏：如果理由可以为空，"不可篡改"就只剩形式——谁也说不清这 0.5 分是为什么加的。

### M1.2 周期状态机

**交付**
- `Term` 表与 `DRAFT → ASSIGNING → ENTERING → PUBLISHED → PUBLIC → ARCHIVED`
- **时间从可注入的时钟读**（`Clock` 接口），不直接调 `Date.now()`
- 发布时写死 `published_at`；锁定时刻 = `published_at + 72h`

**验收测试**（`tests/invariants/term.test.ts`）
- [ ] 把时钟拨到 `published_at + 68h` → 允许申诉
- [ ] 拨到 `published_at + 73h` → 拒绝申诉
- [ ] 尝试调用"延长窗口" → 断言**该 API 不存在**（不是返回 403，是根本没有）
- [ ] 从 `DRAFT` 直接跳 `ENTERING` → 抛错

> `Clock` 接口是整个项目最值钱的一个抽象。没有它，72 小时窗口只能靠真的等三天来测。

### M1.3 录入与冻结

**交付**
- `ScoringItem` / `Department` / `Slice`（用迁移里的种子数据）
- `Slice` 状态：`OPEN → SUBMITTED → REVIEWED → FROZEN`
- 超上限**拒绝写入**（设计文档 §5.5）
- **两种计分模式**：`ACCUMULATE`（基准 0）与 `BASELINE`（基准可配，只录扣分，设计文档 §5.6）

**验收测试**（`tests/invariants/slice.test.ts`）
- [ ] 负责人录入即入账，产生 `ENTRY` 事件
- [ ] 录入使该生该计分项超上限 → 拒绝，且**数据库里没有留下任何事件**
- [ ] `SUBMITTED` 后负责人再录入 → 拒绝
- [ ] 三级顺序错乱（部长先于副部批准）→ 拒绝
- [ ] `FROZEN` 后任何人直接录分 → 拒绝
- [ ] **`BASELINE` 模式下，无人录扣分的学生得分 == 基线分（5），而不是 0**
- [ ] **`BASELINE` 模式下，尝试录入正向 `delta` → 拒绝**
- [ ] **子项间不可调剂：A7-5 超上限时，不能被"挪用"到 A7-1 的余额里**

> "超限时数据库里没有留下任何事件"必须显式测——事务边界写错时，最常见的症状就是留下一条半截事件。
>
> 基线制那条是本项目**最容易被静默做错**的地方：若 A6 按累加制实现，147 名学生每人少 5 分，且因为所有人一起少，排名看起来依然"正常"，没有任何人会察觉。

### M1.4 发布与自动锁定

**交付**
- 发布：已冻结分片计入，未冻结分片写「统计未完成」标记（设计文档 §6.1）
- 定时任务：到点自动 `PUBLISHED → PUBLIC`
- 学生只能查到自己

**验收测试**
- [ ] 发布时存在未冻结分片 → 该分项按 0 计且带「未完成」标记
- [ ] 发布后学生 A 查分只能拿到 A 的记录，查 B 返回空
- [ ] 时钟推进 72h 后跑一次任务 → 状态自动变为 `PUBLIC`
- [ ] 跑两次任务 → 只发生一次状态转移（幂等）

### M1.5 申诉链路

**交付**
- 申诉：指定计分项、理由非空、材料必传
- 链路 负责人 → 副部长 → 部长
- 每级 24h 超时自动升级
- 回避规则：审批人 == 申诉人则跳过该级
- 三级全过才写 `APPEAL_GRANT` 事件

**验收测试**（`tests/invariants/appeal.test.ts`）
- [ ] 三级全过 → 追加 `APPEAL_GRANT`，重放后分数确实变了
- [ ] 任一级驳回 → 分数不变，且写入 `REJECT` + 理由
- [ ] 同一计分项被驳回后再申诉 → 拒绝
- [ ] 申诉人就是负责人 → 断言初审被**跳过并记录跳过原因**
- [ ] 负责人 25h 未处理 → 自动升级到副部长，且升级动作留痕
- [ ] 72h 内提交但窗口关闭时仍在流程中 → 断言**继续走完**，不被作废

> 最后一条是公平性底线：学生按时提交了，审批人慢不该由学生承担。

### M1.6 极简公示页

**交付**
- 一页服务端渲染的 HTML，展示：学生分数 + 该生的完整事件流
- **统计完成情况总览**：逐个计分项显示「已统计 N 条 / 已统计·0 条 / 未提交 / 未指派」（设计文档 §6.4）
- 只读

**验收测试**
- [ ] 页面包含每条事件的 `{时间, 操作人, 分值变化, 理由}`
- [ ] 页面显示链校验状态
- [ ] **区分「已统计·0 条」与「未提交」**：构造一个分片冻结但零记录、另一个分片未提交，断言两者在页面上显示不同
- [ ] 基线制计分项的基线分在页面上可见（回答"为什么大家都是 5 分"）

**阶段一结束的检查点**：拿着这个页面问自己一句——"如果我是想作弊的部长，我能做什么？" 如果答案是"什么也做不了"，内核就是对的。

## 3. 阶段二：横向铺开

### M2.1 身份与权限

- 名册导入（学号 + 姓名 + 班级）
- 三要素注册（学号 + 姓名 + 身份证后 6 位）+ 密码
- `Membership` 表（任职记录，含任命人与任期）
- 干事加入申请 → 部长审批
- 主席任免部长/副部；管理员任命主席
- `domain/permission.ts` 权限矩阵落地

**验收测试**
- [ ] **权限矩阵驱动生成**：7 角色 × N 动作全覆盖，逐个断言 allow / deny
- [ ] 部长读取其他部门负责的计分项 → 返回空
- [ ] 遍历全部 API 路由，断言**不存在 ADMIN 直接加分的路径**
- [ ] 干事未经分派 → 无任何录入权
- [ ] 干事身份变更后，A2-1 干部加分名单随之变化（验证加分读的是 `Membership` 而非注册自选）

> 倒数第二条是设计文档 §7.4 规则一的守门测试。它测的不是"管理员不该加分"，而是"**系统里没有这个功能**"。

### M2.2 全套计分项与责任指派

- 导入 25 个 A 项子项 + C 项条目类型（附录 A 作为种子数据）
- 主席/管理员逐项指派 `计分项 → 部门`
- **有漏项则拒绝进入录入**，并列出漏项

**验收测试**
- [ ] 漏 1 项 → 进入录入被拒绝，错误消息**列出具体是哪一项**
- [ ] 指派后修改 → 旧指派保留在历史里
- [ ] 换一个年级/部门的切片 → 不需要改任何代码

### M2.3 匿名异议 + 双签

- `Objection` 表**不含任何指向用户的列**
- 限流：`HMAC(学号, 服务端密钥)`，同公示期最多 2 条
- 主席 + 管理员双签；可加可减
- 公示期满有未裁决异议 → 拒绝归档并告警（设计文档 §8.5）

**验收测试**
- [ ] **断言 `objection` 表 schema 中不存在 user 外键或等价列**
- [ ] **遍历代码库，断言不存在任何按哈希反查用户的函数**
- [ ] 同一账号提 3 条 → 第 3 条被限流拒绝
- [ ] 只有主席签 → 不生效；只有管理员签 → 不生效；双签 → 生效
- [ ] 公示期满仍有待处理异议 → 归档被拒绝，且顺延天数出现在公示页

> 前两条是设计承诺的守门测试。**匿名靠"查不到"保证，不靠"我们不查"。**

### M2.4 前端（手机浏览器优先）

- 学生：看自己的分 / 发起申诉 / 发起异议
- 负责人：分片录入工作台
- 部长/副部：复核批准 + 申诉审批 + 干事审批
- 主席：全院看板 + 责任指派 + 发布 + 双签
- 公示页：全量 + 事件流 + 异议处理记录

**验收测试**
- [ ] 每个角色的可见范围与服务端返回严格一致（前端隐藏不算数，服务端必须已经拒绝）
- [ ] 学生页面不存在任何他人的分数数据（**检查接口响应体，不是检查页面**）

## 4. 阶段三：加固与交付

### M3.1 B 项导入（确定性识别，不接 AI）

完整设计见设计文档附录 C。实现要点：

- 遍历所有工作表，按「学号正则 + **名册命中率** + 表头关键词 + 数值范围」识别候选列
- 多重候选时列出全部让管理员选，**不自动决定**
- 失败诊断必须具体到列和数字（禁止"格式错误"）
- 提交前显示与上次导入的差异；变动比例 > 30% 要求二次确认
- 幂等 UPSERT；原件存 `data/imports/`；每次导入写 `import_jobs` 审计记录
- B 项**不写 `score_events` 账本**（账本记人的判断，导入记数据的搬运）

**验收测试**
- [ ] 同一份文件导入两次 → 结果与导入一次相同
- [ ] 喂一份"学号列是身份证号"的文件 → 断言报错信息**包含命中率数字**，而非"格式错误"
- [ ] 喂一份多工作表、表头有合并单元格、学号是文本型的真实教务导出 → 能正确识别
- [ ] 把 B 分列错认成 A 分列 → 断言差异比例超阈值并触发二次确认
- [ ] 名册中缺失的学号 → 被跳过且可导出为 CSV，不静默丢弃
- [ ] 断言 `b_scores` 的写入不产生任何 `score_events` 记录

### M3.2 公示表导出
- 沿用现有 Excel 格式（`25级综测成绩*.xlsx` 的两行合并多级表头）

**验收测试**
- [ ] 导出的 xlsx 表头结构与原表一致，能被原表格直接打开
- [ ] 导出的 A 项分值 == 账本重放结果

### M3.3 运维
- 每日 SQLite 快照
- 每日链尾哈希存档（**开发阶段落本地文件**，有真实邮箱后切换为邮件外发）
- 存档失败 → 重试 + 告警

**验收测试**
- [ ] 存档失败时任务不静默成功，产生告警记录
- [ ] 用历史存档校验当前链 → 通过

### M3.4 部署（延后，非当前阻塞）
- Dockerfile / systemd unit
- Caddy 自动 HTTPS + 域名备案
- `docs/运维手册.md`：备份、恢复、开学配置、换届交接

**验收标准**：让一个没参与开发的人，照着手册把系统跑起来。

## 6. 已知风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 学生会没有动力用限制自己权力的系统 | 项目做完没人用 | 这是需求方要解决的政治问题，不是技术问题。技术侧的应对是**降低使用成本**：录入要快，别让人为了合规多花三倍时间 |
| 责任指派在开学时填错 | 分数归错部门 | 未指派禁止录入 + 公示期公开"谁负责这一项"，填错会被看见 |
| 主席/部长换届后不交接 | 系统停摆 | 运维手册含换届清单；`Membership` 有任期，新旧交接可查 |
| "完全匿名"被内部人质疑 | 信任危机 | 不靠口头保证，靠**可验证的 schema 断言测试**，随时可跑给任何人看 |
| 2000 人规模超出 SQLite | 性能问题 | 数据量离 SQLite 上限极远；真到瓶颈时迁移 Postgres，账本层代码不用改 |
